## 5. Архитектурные решения

1. **Модель, шум и метрика разделены.** Функции кодеков ничего не знают про канал, канал —
   про коды, BER считается только в `metrics.py`. Каждый слой можно тестировать отдельно.
2. **Ядро — чистые функции.** `hamming.encode(bits) -> bits`, `convolutional.encode(bits) -> bits`,
   `viterbi.decode(bits) -> bits`, без глобального состояния. Исключение — `rng`, он всегда
   передаётся явно. Решётка строится один раз и кэшируется.
3. **Один источник истины для R.** Фактическая скорость `R = L / (2*(L+2))` для свёрточного кода
   и `R = 4/7` для Хэмминга. Значение пишется в CSV вместе с каждой точкой и используется
   и в `sigma²`, и в подписях графиков.
4. **BER — только по информационным битам.** У всех схем длина сравниваемых массивов равна
   числу переданных информационных битов; хвостовые биты в подсчёт не входят.
5. **Детерминированность.** Единственный источник случайности — `numpy.random.default_rng(seed)`;
   отдельные независимые потоки (данные и шум) создаются через `SeedSequence.spawn`, чтобы
   изменение объёма шума не меняло информационные биты.
6. **Данные → файл → график.** Notebook не рисует по объектам в памяти, если есть сохранённый
   CSV: так график воспроизводится из артефактов репозитория.
7. **Быстрый и полный режимы отдельно.** Демонстрационный прогон занимает секунды, полный
   эксперимент — минуты; полный запускается только явным действием.

## 7. Вычислительная стоимость

Предварительная оценка; фактические замеры — в `results/data/performance_probe.json`.

Планка задания: ≥10⁶ информационных бит на точку, 11 точек (0…10 дБ), 3 схемы,
целевое число ошибок ≥100.

- **Без кодирования:** 11 · 10⁶ бит — это секунды. Но при 8–10 дБ BER получается
  4·10⁻⁴…4·10⁻⁶, то есть на 10⁶ бит приходится **меньше 100** ошибок → нужно около 3·10⁷ бит
  на точку (примерно 30 с, память позволяет за счёт блочной генерации).
- **Хэмминг:** векторизуется в NumPy поблочно, поэтому стоит примерно как некодированная схема.
- **Свёрточный код:** Витерби O(N·S) при S=4. Пакетная реализация (B блоков параллельно,
  массивы `(B, 4)`) даёт около 10⁶ бит за несколько секунд; узкое место — обратный проход
  traceback (память `L·4` байт на блок).
- **Главное ограничение — не время, а достижимая статистика:** при 10 дБ BER кодированных
  схем порядка 10⁻⁸…10⁻⁹, а это 10⁹…10¹⁰ бит. Такие точки помечаются как «ниже разрешающей
  способности» с указанием верхней границы.

Итог по остановке: критерия остановки по числу ошибок в проекте **нет**. План фиксированный —
объём на точку задан заранее и не меняется по ходу счёта. `time_budget_s` в `Plan` нужен только
для диагностики: если точка считалась дольше бюджета, в CSV попадает статус `ok_over_budget`
(это пометка о времени, а не о точности). Диапазон Eb/N0, объёмы и seed зафиксированы
в спецификации (Q8, Z1, Z4).

### 7.1. Бюджет времени полного прогона (зафиксирован 24.10.2026)

Полный эксперимент должен уложиться в **15–30 минут** суммарно (3 схемы × 11 точек). Следствия:

- по времени ориентир был 30–60 с на точку; в коде `Plan.time_budget_s = 120` с — это порог
  для пометки `ok_over_budget`, а не команда останавливаться. Объём — 2·10⁶ бит для
  некодированной схемы и Хэмминга, 10⁶ бит для свёрточного кода (в расширенном прогоне
  в 10 раз больше);
- целевые 100 ошибок набираются только при Eb/N0 ≲ 5 дБ; для 6…10 дБ точки идут с фактическим
  числом ошибок и пометкой о точности (правило Q9). Это **свойство статистики, а не ошибка
  реализации**;
- демонстрационный режим остаётся отдельным и занимает секунды; notebook полный прогон
  автоматически не запускает.

Объёмы берутся из принятого плана (Q8) и вынесены в параметры `Plan`, поэтому расширение плана
не требует переписывать код.

## 8. Что лежит в CSV

`results/data/ber_results.csv`, одна строка = (схема, Eb/N0). Фактический набор колонок
определяет `src/simulation.py` (`write_csv`); в сохранённых файлах он такой:

```
scheme, ebno_db, n_info_bits, n_tx_bits, n_errors, ber,
n_units, n_units_with_errors, sum_z2, z_hist,
ci_type, ci_level, ci_low, ci_high, upper95,
cluster_low, cluster_high, cluster_se,
r_nominal, r_eff, sigma2, ell, length, tail_bits,
seed, status, elapsed_s,
numpy_version, python_version, timestamp,
x_n_units_with_errors, x_unit_ell
```

`ber = n_errors / n_info_bits` без округления. `upper95` заполняется только для точек с нулём
ошибок — это консервативная верхняя граница (правило Q9). Колонки `z_hist` (гистограмма
числа ошибок в независимой единице), `n_units`, `n_units_with_errors` и `sum_z2` нужны для
кластерных интервалов и bootstrap. Префикс `x_` — поля из `extra`.

Замеченное расхождение: в списке колонок `write_csv` есть ещё `dataset` и `streams`, а в
сохранённых CSV их нет. То есть свежий прогон `run_experiment.py` дописал бы две новые колонки.
Сами данные от этого не меняются, но состав колонок сверяется при проверке, поэтому вопрос
о том, приводить ли файлы к текущему писателю, оставлен открытым.
